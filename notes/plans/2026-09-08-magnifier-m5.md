# M5 보이는 화면 영역 A/B 직접 전달 계획

## 1. 목표

사용자가 선택한 화면 사각형은 특정 앱 창이 아니라 현재 보이는 데스크톱 표면이다. 미리보기에서 A와 B를 찍으면 표식 중심과 클릭 지점이 일치하고, 두 지점의 직선 계획이 즉시 보인다. 실제 실행은 그 두 점이 뜻하는 물리 화면 좌표에 한 번의 `Down(A) → Move(B) → Up(B)`을 전달한다.

브라우저 마스크 페인팅과 Blender 5.2는 이 동작을 확인할 두 표면이다. 런타임에는 창 핸들 탐색, 한 창 제한, 앱별 분기, 브러시·레이어 제어를 넣지 않는다.

## 2. 수락 기준

- `A 지정` 뒤 이미지 클릭은 A 표식의 중심을 해당 렌더링 이미지 좌표에 놓는다. B도 동일하며, letterbox·창 크기·DPI 변화 뒤에도 표식과 클릭 의미가 달라지지 않는다.
- A와 B가 모두 지정되면 두 표식 중심을 잇는 직선 계획이 즉시 보인다. hover만으로 추가 원·점·입력은 생기지 않는다.
- 실제 A→B 실행 직전 미리보기는 선택 영역의 전역 클릭을 가로채지 않는다. 실행 뒤에는 성공·실패·취소와 무관하게 즉시 복귀한다.
- 입력 목적지는 선택한 `ScreenRegion`의 물리 화면 좌표다. 브라우저·Blender·기타 창을 식별·제한하지 않는다.
- 시작 상태의 실제 입력은 꺼져 있다. 사용자가 실제 입력을 허용할 때에는 미리보기의 실행 제어와 같은 줄에서 상태를 명확히 바꾸며, 뒤의 기본 창에서 제어를 찾게 하지 않는다.
- Esc·창 닫기·capture 손실·gate 해제 뒤에는 `LeftUp`을 한 번 시도하며, 실제 입력 성공을 추측해서 표시하지 않는다.

## 3. 현재 근거와 미확정 사항

이미 확인한 근거:

- 미리보기 창은 캡처 제외 상태라 선택 영역과 겹쳐도 자기 창이 프레임에 중첩되지 않는다.
- A/B 표식은 정수 `ScreenPoint`와 분리한 정규화 좌표로 배치되며, 사용자가 표식 중심과 클릭 위치의 일치를 확인했다.
- 기준 빌드는 경고·오류 0이고 Core 테스트 7개가 통과했다.

현재 확인한 결과:

- App 변경은 표준 실행본으로 build/relaunch했고 build 경고·오류 0, Core 테스트 7개를 확인했다.
- 사용자는 A/B 전용 흐름이 확대된 화면을 계속 조작하는 실제 돋보기가 아니며 실시간 조작이 동작하지 않는다고 확인했다. 따라서 M5는 완료가 아니라 `BLOCKED`다.

## 4. 실행 순서와 소유 범위

1. 실행 중인 Magnifier를 닫고 표준 출력 경로에서 build/test한다. 이전 exe와 새 소스를 혼동하지 않는다.
2. 새 실행본에서 영역을 선택한다. 미리보기의 같은 조작 줄에서 실제 입력 상태를 확인한 뒤 A와 B를 지정한다.
3. 미리보기의 렌더링 좌표·표식 좌표·A/B 입력 좌표를 같은 변환 규칙으로 확인한다. 불일치가 보이면 App의 해당 변환/표식 코드만 차단 문제로 수정한다.
4. 실제 A→B 직전에는 미리보기를 잠시 숨겨 전역 `SendInput`의 수신자가 선택 화면 아래 앱이 되게 한다. Core 세션과 Infrastructure `SendInput` 계약은 새로 일반화하지 않는다.
5. A/B 한 획 검증과 별개로, 실시간 조작 모드가 확대 좌표를 지속해서 받으며 아래 화면에 Down → Move → Up을 전달하는 구조를 설계한다. 브라우저와 Blender에서 실제 짧은 드래그와 Esc release를 확인하기 전에는 완료로 처리하지 않는다.

허용된 코드 범위는 검증에서 확인된 차단 문제에 한해 `src/Magnifier.App`, `src/Magnifier.Core`, `src/Magnifier.Infrastructure`다. 현재 예상 변경은 App의 미리보기와 상태 동기화뿐이다.

## 5. 검증과 기록 규율

- 명령: `dotnet build Magnifier.slnx --nologo`, `dotnet test Magnifier.slnx --nologo`.
- 수동 확인은 브라우저와 Blender 각각에서 `표식 일치 → 직선 계획 → 실제 A→B 전달 → 실시간 짧은 드래그 → Esc 취소` 순서로 기록한다.
- 실행 중인 exe에 없는 UI·동작은 존재한다고 안내하지 않는다. build·relaunch·수동 확인 전에는 `검증 전 변경`으로만 쓴다.
- 실제 입력의 성공·실패는 화면에서 관찰한 결과로만 기록한다. 실패 시 대상 창 제한이나 앱별 우회로를 추가하지 않고, 좌표·창 겹침·권한·취소 상태 중 관찰된 차단 원인만 수정한다.

## 5.1 현재 차단과 재설계 범위

현재 A/B 전용 화면은 일반 미리보기 클릭을 실제 입력으로 보내지 않는다. 이전 방식은 미리보기 자신이 전역 입력을 받거나 실패 후 gate를 끄는 문제를 만들었다. 이는 의도한 실시간 돋보기 조작이 아니다.

다음 설계는 아래를 동시에 만족해야 한다.

- 확대된 조작 표면에서 지속적인 Down → Move → Up 좌표를 받는다.
- 실제 입력은 선택한 보이는 화면 아래로 전달하며, 미리보기 자신이 대상이 되지 않는다.
- 미리보기를 숨기거나 click-through으로 바꿀 때에도 조작 좌표·mouse capture·실시간 프레임 갱신·Esc release를 잃지 않는다.
- A/B 한 획은 보조 기능으로 유지하되, 실시간 조작과 같은 이벤트 경로로 암묵적으로 섞지 않는다.

이 설계가 정해지기 전에는 추가 source 변경을 시작하지 않는다.
